# R4 API implementation report

November 4, 2026. This report supersedes the single-Coding increment in [API_CODING_REPORT.md](API_CODING_REPORT.md). The agreed boundary is the term-squid product API: six declared R4 terminology operations, public resource browsing, separate authenticated administration and their documented limits. Additional operations, public authoring and new FHIR release adapters are not part of this boundary.

## Contract and behavior

[R4_API_CONTRACT.json](R4_API_CONTRACT.json) records all **70 top-level input parameters** from six pinned R4 OperationDefinitions, their input/output structures, source checksums and acceptance-test references. Counts are lookup 7, CodeSystem validation 10, subsumption 6, expansion 21, ValueSet validation 13 and translation 13. The inventory tracks implemented behavior, not merely parameter acceptance or unsupported-operation responses. Final delivery validation passes; see the evidence section for the exact source, artifact and runtime checks.

- Lookup accepts primitive/Coding identities, versions, dates, repeated requested properties and display languages. Definition is a typed property; actual designation use is a Coding. An unnamed system falls back to its real canonical rather than an empty FHIR string. Rich lookup reads bounded source metadata or native RF2 descriptions and inferred parent/child edges. Corrupt stored properties remain errors even when properties are selected.
- CodeSystem and ValueSet validation accept primitive, Coding and CodeableConcept forms. Any valid candidate succeeds; an unavailable or indeterminate candidate is not converted into a definitive negative when none succeeds. All candidates use one read-only snapshot. Inline CodeSystem complete/fragment, case rules, abstract policy, language/designation display validation, historical selection and unambiguous local system inference are implemented. UCUM remains database-independent for its bundled canonical edition.
- Subsumption accepts independent primitive/Coding A/B forms and preserves the four outcomes. System/version and instance metadata share the hierarchy snapshot. Unestablished cross-system relationships remain indeterminate. The existing instance extension continues ignoring the legacy top-level version selector; typed Coding.version remains an assertion.
- Expansion supports stored, instance, inline and local-context roots; independent ValueSet versions; transitive default/check/force system versions; date; code/display filtering; offset/count; active/selectable/post-coordinated policy; system exclusions; definition/designation inclusion; designation language/use tokens; display language and bounded nested results. Filtering/localization happens before counting and paging. Native expansion returns one page without fetching an entire code system into application memory. Explicit includeDesignations=false suppresses designations even when a selector is supplied. Version overrides are recorded in expansion parameters.
- Translation supports primitive/Coding/CodeableConcept, input and map business versions, inline maps, local map discovery, source/target ValueSet context, targetsystem, reverse, repeated dependency parts, products and source provenance. It implements provided/fixed/other-map rules, cycle/depth guards and bounded reverse fixed enumeration. Explicit negative mappings never enter unmapped fallback. Complex discovery, dependencies and memberships share one transaction snapshot; ordinary selected-map requests retain the prepared-map path.

CodeSystem supplements are supported without changing the base coding identity. Additional designations/properties enrich explicitly rich lookup and validation, finite composition and localized native results. Supplemental language selection happens before native expansion filtering/counting/paging; projected designation storage avoids fetching native code systems. Base codes and property values are verified before atomic activation; supplements cannot introduce codes or override existing values, displays or definitions. Latest applicable supplemental versions and historical publication selection use the reader snapshot. Package publication acquires identity locks in global order and then imports base systems before supplements. The ordinary preferred-display lookup path retains its base default properties; callers request language/properties/designations to use supplemental metadata. UCUM's plain grammar reads remain database-independent; optional localized supplemental metadata uses the standalone database.

R4 GET/POST operation extractors reject unknown, duplicated and mixed representations. Repeated primitive query parameters are preserved. Accept quality/specificity, JSON aliases, `_format` precedence, media versions and UTF-8 content types are negotiated without authentication or database access. Errors, unknown FHIR paths and unsupported methods return OperationOutcome; 405 preserves Allow. API fallbacks do not become SPA HTML.

`GET /r4/metadata?mode=terminology` and `/r4/TerminologyCapabilities` provide a fresh local CodeSystem/version/default/provider inventory with supported declared filters/properties. `/r4/OperationDefinition/{CodeSystem-lookup,CodeSystem-validate-code,CodeSystem-subsumes,ValueSet-expand,ValueSet-validate-code,ConceptMap-translate}` exposes the pinned structural contracts. The CapabilityStatement describes actual behavior and the verified R4 adapter.

## Explicit policies and bounds

The standalone context registry resolves a local ValueSet canonical or `ValueSet/{uuid}`. Incoming/outgoing use the same selected binding. No StructureDefinition conformance registry is provisioned; fragment binding contexts fail explicitly with a useful alternative. Context URIs never cause remote requests or filesystem reads.

Historical inference selects definitions by their declared date or native RF2 release date. Updated-at ordering is not a clinical date. An explicitly selected immutable edition can be used without inferring a different historical edition. Missing historical information fails explicitly; caller-supplied definitions published after the requested date are rejected. Partial year/month/day requests include their calendar interval through its end. Display lookup uses the requested language range with fallback; validation accepts matching real designations in the requested language and returns the preferred available display.

Shared limits remain 64 parameters/candidates, 4,096-byte text fields, 2-MiB operation bodies, bounded 256-KiB inline roots, 128 dependencies, 100,000 finite concepts, 32-level traversal and 10,000 response entries. Complex services share four execution slots, a bounded request admission and a 15-second deadline; SQL statements have a ten-second limit. CPU work retains its permit if the waiting request is cancelled. Map/source metadata is bounded at 32 MiB; designations at 256 per concept; reverse fixed mappings cannot return a partial source enumeration. Nested expansion requires a complete bounded page; RF2 multiple parents use a deterministic parent for presentation. Supplement metadata is bounded at 32 supplements per base and 128 selected supplemental dependencies; supplemental version inventories have explicit bounds. Historical supplements require publication dates. Native custom supplement filter expressions beyond the native provider filter inventory fail explicitly. Metadata inventory is bounded at 10,000 installed versions and 32 MiB. These limits are errors, not invented progress or incomplete successful expansions.

Native provider knowledge remains the documented subset: no ECL/refset completion, LOINC accessory corpus, RxNorm provider or general UCUM ValueSet grammar enumeration is claimed. Malformed/unsupported clinical expressions stay explicit errors. CodeableConcept validation does not implicitly translate through ConceptMaps. The adapter is not a general FHIR profile validator; existing primitive aliases and legacy stored-property compatibility remain. R5/R6 aliases are not verified adapters. No clinical coverage, performance ranking or complete licensed corpus is claimed by this API checkpoint.

## Architecture, administration and build

The storage-independent Rust engine retains immutable prepared structures. Shared compose loading is reused by cached reads, multi-code validation, rich expansion and map scope evaluation. Complex operations use repeatable-read snapshots and bounded worker admission. Existing generation observation, immutable imports, atomic publication/rollback and cross-process freshness tests remain. No session/authorization query was added to public terminology hot paths; the public pool remains independent of administration.

Administration remains `/api/admin`, with bootstrap Argon2id hashes, revocable expiring server sessions, HttpOnly/SameSite cookies, Origin/CSRF checks before upload IO and persistent bounded import jobs. No default credentials or public registration were introduced. Bootstrap, supported JSON/package formats, cancellation/recovery/retention and the existing migrations are documented in [UI_ADMIN_IMPLEMENTATION_REPORT.md](UI_ADMIN_IMPLEMENTATION_REPORT.md) and [PACKAGE_IMPORT_REPORT.md](PACKAGE_IMPORT_REPORT.md). Apply **20261104000006_supplements** before running this backend/CLI: it adds the bounded designation projection and supplement-target index and backfills existing supplemental designations. Existing native manifests and source fingerprints remain unchanged.

React 19 and the actual UI-kit delivery remain pinned to server-rs revision `5a17d7428e8da253fcd87375e45b41c89ff59997`, using pnpm's Git subdirectory selector. Node 24.16.0 and pnpm 10.11.0, the frozen lockfile, source exports/aliases and self-hosted licensed assets are unchanged. Developers/CI need Git read access to the SSH repository. No sibling checkout or OctoFHIR process/database is a build/runtime dependency. Build the frontend before Cargo/RustEmbed. New Rust dependencies are pinned serde_html_form 0.2.8 plus direct form_urlencoded/mime use from the lockfile.
