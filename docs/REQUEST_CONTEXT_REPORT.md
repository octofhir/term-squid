# Request-local terminology resources

November 4–5, 2026. This increment implements the `tx-resource` protocol for the six public R4 operations without importing temporary content. The official Java runner's original `case` setup now passes on an empty standalone database. This supersedes the original setup-mode limitation in [ECOSYSTEM_R4_REPORT.md](ECOSYSTEM_R4_REPORT.md); it does not establish complete ecosystem certification.

## Public contract and resolution

Public operation POST bodies may include repeated `Parameters.parameter` entries named `tx-resource`, each containing exactly one R4 CodeSystem, ValueSet or ConceptMap resource. `value[x]`, `part`, mixed forms and unsupported resource types fail. The middleware applies only to public operation routes, including instances; ordinary GET and POST resource browsing and administrator authentication remain separate. Public read POSTs do not acquire session/authorization queries.

Temporary definitions are immutable and exist only while that operation future is polled. The store overlays them during lookup, CodeSystem/ValueSet validation, expansion, subsumption and translation. Imported ValueSets, source/target scopes, discovered ConceptMaps, chained maps and reverse fixed mappings use the same context. Definitions never enter a database table, upload staging, import job or retained plan cache. A subsequent request cannot see them. Spawned tasks do not inherit the context implicitly; preparation receives owned inputs explicitly.

Identity is resource family plus canonical URL plus business version. Exact duplicate definitions are deduplicated while preserving their last request position; different definitions of the same identity fail. A canonical containing a version must agree with a separate version parameter. Among supplied editions, an unversioned reference selects the last matching definition in request order. Historical selection instead chooses the latest eligible publication date, breaking ties by request order. Explicit immutable editions without publication dates retain the existing policy. Temporary definitions take precedence over matching stored references; unresolved dependencies use the normal repeatable-read database snapshot. Supplied resource IDs never replace stored instance identity.

Bundled UCUM and native LOINC/SNOMED CodeSystem identities cannot be overridden. A temporary ValueSet can reference an installed native release through the existing projection provider. Existing unsupported mixed native/finite and provider-expression cases remain errors. Temporary supplements initially require their finite base CodeSystem in the same request, select one eligible edition per supplement canonical, and use the shared supplement validator/merger. They cannot add codes or replace the base display/definition. Supplements of stored/native bases without a supplied finite base remain explicitly unsupported.

## Bounds, cancellation and retained plans

The request context allows at most 32 resources, 256 KiB of serialized source per resource, 1 MiB aggregate source, 100,000 aggregate concepts and the core's 32-level nesting limit. Enrichment is limited to 1 MiB per resource and 2 MiB aggregate. Existing compose, map, page, traversal, statement and response budgets remain in effect.

Public read-operation POST admission permits at most 64 in-flight requests, acquired before reading the bounded JSON body. Context work permits four executing preparations/operations. A 15-second deadline includes body reading, waiting for preparation and running the operation. Slow, malformed and overloaded bodies cannot bypass this admission budget; GET retains its existing path. Administrator routes retain their separate authorization-before-body policy. CPU preparation uses Tokio's blocking worker pool rather than an HTTP reactor thread; it does not execute synchronous database I/O or shell out to the CLI. A cancelled request signals preparation to stop at the next resource boundary. A core call already preparing one bounded resource is not forcibly preempted and keeps its work permit until it returns. Existing operation preparation similarly owns its admission permit through computation. Timeout must not be described as instantaneous CPU or PostgreSQL cancellation.

Context operations bypass every global retained-plan lookup and publication, even when only a dependency of a stored root is overridden. They also avoid retained-plan generation observations and the global cold-plan single-flight mutex; bounded operation work admission replaces that mutex. Stored readers still use the existing fresh generation boundary and immutable snapshots. Context content cannot poison a retained positive or negative result.

Result membership and compact code knowledge are owned, so plans do not retain the shared view.

Lookup-capable R4 preparation records an otherwise unsupported lifecycle policy without changing lookup availability. Shared composition enforces exactly the same complete-source/lifecycle admission as strict R4 preparation. Resource/concept budgets, identity conflicts, partial grammar coverage and ordinary/contained/imported selection behavior remain bounded. ## Related finite semantics, provenance and validation

The reusable engine adds an opt-in `PreparedSystem::prepare_for_r4`. Formal property URIs and declared types carry their actual meanings, including aliases of standard inactive/abstract/not-selectable booleans. Custom same-spelled properties with unrelated URIs are not silently treated as these flags. Explicitly declared standard status recognizes active, experimental, deprecated and retired; retired members are inactive. Unknown/custom lifecycle rules, contradictory retired/inactive flags, graph aliases and date-transition policies remain errors. The conservative existing `prepare` API and its rejection assertions are preserved. See the [R4 concept-status definition](https://www.hl7.org/fhir/R4/codesystem.html#status).

The finite R4 provider validates actual property value types, standard URI/type consistency and contradictory boolean aliases before evaluation. `prepare_for_r4_source` applies these checks to partial inline/temporary resources without claiming unknown codes in incomplete content are invalid. The finite R4 provider adds typed `in`/`not-in`, bounded full-match `regex`, R4 `generalizes` and an explicitly identified `child-of` compatibility extension. Case-insensitive code filters and hierarchy anchors resolve through one compiled canonical-code dictionary. Regex uses the existing locked `regex-automata` 0.4.18 dependency without backtracking: at most 32 expressions, 1,024 source bytes, 32 syntax nesting, 64 KiB NFA per expression, 1 MiB aggregate compiled memory and 4,096 bytes per input scalar. Membership permits at most 256 nonempty scalar values within 4,096 bytes. Unsupported syntax/types remain errors. Native providers retain their separate filter inventories. Incomplete finite hierarchies cannot establish a definitive public subsumption result: the API returns an explicit indeterminate error and capability versions omit complete hierarchy filters. Raw projection readers retain their existing behavior. Native `content=not-present` resources still use their real installed projections.

Graph preparation validates ordinary shallow DAGs once, with a bounded shortest-path fallback preserving existing shortcut-DAG depth semantics. It retains the 32-depth and one-million-relationship limits, with ten million edge visits. Finite composition has a ten-million-work budget and an eight-MiB bounded memo for small shared imported sets; cached subtrees cannot bypass import depth limits. These are operation limits, not latency guarantees.

Expansion plans/pages retain actual selected CodeSystem, imported ValueSet and supplement editions. Responses report these through `used-codesystem`, `used-valueset` and `used-supplement` expansion parameters, including empty/zero-count finite results. Native provenance uses already resolved releases; it does not load entire native systems. The cache memory charge includes this metadata. Requested pagination is echoed; a default count is reported if it actually truncates results. An absent zero offset is omitted. Existing bounded counts, total semantics and per-concept business-version output remain.

Validation version directives (`system-version`, `check-system-version`, `force-system-version`) are documented client extensions on ValueSet validation only. GET and POST reuse expansion's same-snapshot version selection; an asserted Coding version is never silently overridden. The seventy normative R4 top-level inputs remain unchanged. The explicit `lenient-display-validation` boolean extension converts only a display mismatch to a warning; strict validation remains the default. Unknown codes, membership, version and abstract-policy failures are never promoted to success.

Finite plans retain compact code knowledge for their actual selected CodeSystem editions, charged to the existing retention budget. Negative Coding/CodeableConcept diagnostics distinguish known codes outside the set from unknown codes in complete systems using this same snapshot, without a second latest-version resolver query. Native negatives remain conservative. Detailed object results include system, code, case normalization and OperationOutcome field paths such as `CodeableConcept.coding[1].display`. Primitive forms preserve their established response contract.

Display validation accepts actual source designations and respects explicit language selection. A common correct preferred display uses the existing fast path. A mismatch invokes bounded rich validation on a complete new snapshot; newly imported designation projections load only the selected concept's labels, while old NULL projections retain the bounded legacy fallback. The fallback discards the first probe decision, resolves the original client selectors and serializes the entire new snapshot, including a negative result. It never accidentally pins an unversioned request to the probe edition. Explicit edition and instance selectors stay fixed. A PostgreSQL regression test pauses the real first probe, publishes a new immutable edition through shared ingestion, then verifies the complete result in both retention modes. No whole-system fetch is added to ordinary matching-display validation. Version/unknown-code/abstract failures cannot become successful merely because a label matches. Native SNOMED and supplement label projections share the operation's aggregate byte budget; PostgreSQL returns NULL for over-budget JSON before client decoding. Source order and dialect preference are retained. Base plus supplement designations share the same 256-entry per-concept bound; oversize results fail rather than truncating enrichment.

## Required supplement declarations

ValueSet `http://hl7.org/fhir/StructureDefinition/valueset-supplement` declarations are checked against the overlays actually applied to the selected CodeSystem editions. A merely installed unrelated, retired or wrong-version supplement does not fulfill the dependency. Finite and native loaders collect declarations across root, imported, contained and temporary definitions. Missing/inapplicable requirements fail explicitly before a result or retained plan is published. Native reads perform this dependency check even without language enrichment. Malformed declarations fail; the operation permits at most 128 distinct required canonicals, each within 4,096 bytes.

This uses the existing latest/date-based supplement selection policy. An exact requirement must match that selected edition; forcing an older supplement edition is not implemented and cannot silently use a newer one. The original source JSON remains unchanged, and successful responses retain actual `used-supplement` provenance. Installing or retiring an overlay uses the existing transactional generation invalidation.

## Contained ValueSet scope

Local `#id` canonical references resolve in the owning ValueSet's container, including references between siblings and `#` to the container itself. Finite and native projection loaders use the same resolver and existing evaluator/SQL compiler. Same IDs or even child canonical URLs in separate containers cannot collide. Public resource JSON, contained definitions and compose references remain original; internal evaluation identities do not appear in successful public provenance or become registry entries. Cycles and unknown local references fail without external registry fallback.

Contained definitions count against a bounded resource inventory and the containing document's existing byte budget. Invalid/duplicate IDs, unsupported contained resource kinds, nested containment and independent contained version/security metadata fail. Only ValueSet containment is implemented in this increment; external container-fragment URLs and contained CodeSystem/ConceptMap workflows are not advertised as supported. These rules follow [R4 canonical fragments and container scope](https://hl7.org/fhir/R4/references.html#canonical) and [DomainResource containment constraints](https://hl7.org/fhir/R4/domainresource-definitions.html#DomainResource.contained).

## Remaining Unicode comparison boundary

A focused post-timing review confirms an existing difference between PostgreSQL-backed code lookup and the independent finite engine for some non-ASCII case mappings. The fixture is one complete, case-insensitive CodeSystem containing only `U+0130` (LATIN CAPITAL LETTER I WITH DOT ABOVE), imported through the real CLI/shared ingestion path into a fresh disposable database. Stored and request-local lookups send identical source definitions, business versions and codes.

| Query code | Stored lookup | Request-local lookup |
| --- | ---: | ---: |
| `U+0130` | 200 | 200 |
| `U+0069` | 200 | 404 |
| `U+0069 U+0307` | 404 | 200 |

The exact 200-test baseline and final 206-test artifacts both reproduce all six statuses. PostgreSQL lowercasing in the recorded `en_US.utf8` database and Rust Unicode lowercasing produce different comparison keys for this fixture. These twelve diagnostic responses are retained under `.benchmarks/overnight-20261105/unicode-review/`; they are outside every timing window and do not change any benchmark score or claimed conformance count. The review servers stop after capture; preview and matched-content databases are untouched.

The complete source fixture is reproducible without external content:

```json
{"resourceType":"CodeSystem","url":"urn:term-squid:unicode-review","version":"1","status":"active","content":"complete","caseSensitive":false,"concept":[{"code":"\u0130","display":"Dotted capital I"}]}
```

Save it under `.benchmarks/` and import with `term-squid-cli --database-url "$DATABASE_URL" create-code-system FILE` into a fresh disposable database. POST `Parameters` to `/r4/CodeSystem/$lookup` with `system=urn:term-squid:unicode-review`, `version=1` and each code from the table, then repeat with the identical source as a `tx-resource`. Record the database character locale and both full responses. This reproduction does not establish a preferred cross-locale comparison policy.

This remains a consistency limitation, not a newly introduced generation-hint regression. Resolve it through an explicit shared comparison policy covering ingestion/projections, SQL fallback, retained plans, request-local/finite APIs and the standalone engine. Preserve exact-code lookup, Unicode source spelling, ambiguity rejection and cross-process freshness; record any required projection migration/rebuild. Do not silently substitute a database locale for the reusable engine, change old assertions or claim complete Unicode equivalence from the passing ASCII case suite.
